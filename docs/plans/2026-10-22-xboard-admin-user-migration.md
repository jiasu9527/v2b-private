# 管理后台 Xboard 用户迁移

## 范围与入口

管理员后台 **设置 → 用户迁移**（`/config/user-migration`）。仅完整管理员可用；员工、普通用户不可读取源库或执行迁移。使用当前 V2B Go / PostgreSQL 后端，将 Xboard MySQL 普通用户追加到当前站，不调用旧 `merge-mysql` CLI。

本次已确认的资金策略：**正常迁入用户，但不迁移 `locking_balance` 待解锁佣金**。页面默认 `discard`，仍必须显式勾选确认。它不增加账户余额，也不影响原有普通佣金。

## 操作流程

1. 备份源站和目标站数据库，确认恢复方法；安排源站停止相关写入／切换窗口。
2. 填 MySQL 主机、MySQL 端口（默认 3306）、数据库名、数据库账号和密码。这不是 SSH 登录框，不能把 SSH 端口 2222 当数据库端口。
3. 点击“读取用户与套餐”。数据库连接由 **V2B 后端服务器**发起，不是管理员浏览器发起。
4. 手动选择每个源套餐对应的目标站已有套餐；可以明确选择“不迁入这个源套餐下的用户”。源套餐已删除但仍被用户引用时，也会列出供映射。
5. 确认待解锁佣金处理方式并生成只读预览，核对新增数、重复邮箱、权限排除及阻断项。
6. 完成备份和源数据变化确认，输入 `IMPORT_USERS` 后提交。预览有效期 10 分钟；源站后续变化不自动进入已生成快照，必要时重新预览。
7. 保存迁移编号，等待回执。请求中断、超时或暂时查不到回执**均不能证明导入失败**；先查询同一编号，不要盲目新建迁移。
8. 抽查账号登录、余额、套餐分组、已用流量和重置时间，再安排用户切换到目标站订阅地址。

推荐只读 MySQL 用户，仅授予源库 `v2_user`、`v2_plan` 的 SELECT 权限；两表必须为 InnoDB。使用内网、受限 SSH 隧道或证书验证 TLS，数据库防火墙仅放行必要来源。TLS 开关开启后验证服务器证书，不跳过验证。不要开放 MySQL 给所有公网地址。

## 数据处理规则

| 数据 | 处理 |
|---|---|
| 源管理员／员工 | 排除，不降级迁入，不复制后台权限 |
| 目标已有邮箱 | 去首尾空白、不区分大小写比较；整条跳过，原密码和权益不变 |
| 源内重复邮箱 | 第一条普通用户记录优先，其余跳过；预览显示计数 |
| 用户密码 | 保留兼容 bcrypt 哈希，不导出明文；不支持的格式阻止导入 |
| 余额、普通佣金、封禁状态 | 保留，不因迁移解封 |
| 流量额度、已用上／下行、到期时间 | 保留源值，NULL 与 0 不混同；不按目标套餐重新赠送额度 |
| 套餐／权限组／设备数／限速 | 套餐必须映射；使用选定目标套餐的设置，不复用源 group ID |
| 无套餐用户 | 保留原额度、用量、到期和资金；目标 plan/group 为空，不自动赋予目标套餐权限 |
| 流量重置 | 使用目标套餐／系统周期；导入同一事务写入当前周期标记，避免第一次日扫清掉已用流量；不复制 Xboard `next_reset_at` |
| Token／UUID | 格式兼容且无冲突时保留；冲突或不兼容时重生；旧域名不会自动接管 |
| 订单、支付流水、节点、邀请码、邀请关系、Telegram 绑定、个性折扣／佣金比例、会话、自动续费 | 不迁移；目标分配新的用户 ID，自动续费关闭 |
| 待解锁佣金 | 默认明确舍弃该字段，用户照迁；源库保持不变 |

这不是持续同步，也不是对同邮箱权益做合并。提交前目标出现相关邮箱、Token／UUID 冲突，或目标套餐发生变化，会要求重新预览。

## 一致性与凭据保护

- 源库固定两表、只读 REPEATABLE READ 事务，无用户提供 SQL／DSN／表前缀。
- 用户和流量周期标记、完成回执在目标库同一事务内提交。写入采用 500 用户一批；失败回滚，不部分导入。
- 提交期间短时锁定目标用户／套餐表以防注册和改套餐竞争；应在低峰维护窗口运行。锁等待上限 5 秒，整操作上限约 110 秒。
- 同一迁移编号重复提交返回已完成回执；回执绑定发起管理员。数据库提交结果不确定时禁止自动重试。
- 源数据库密码只在本次请求／当前页面内存，不存配置、localStorage、URL 或业务日志。预览中的用户快照只存在后端内存，过期释放；重启后未提交预览失效。
- 仅持久化小型 `v2_user_migration_receipt` 完成记录：迁移编号、操作者 ID、摘要、计数和时间，不保存邮箱、账号密码、Token 或源数据库凭据。
- 不提供“一键删除本次导入用户”；实际完成后需要回滚时应先停写、核对后按数据库备份恢复方案处理，不按时间范围盲删。
- 单次源用户上限 200,000，目标校验上限 2,000,000，内存预览数量和用户总数有上限。大库需要另行安排，不通过无限延长 HTTP 请求处理。
- 多实例部署应保证预览与提交到同一后端实例（或迁移期间单实例）；完成回执存在共享目标库，可跨重启查询。
- 反向代理也应允许此迁移路由的较长响应时间，否则即使后端继续执行，前端也可能先收到网关超时。不要因此自动重提。

## 接口

前缀：`/api/v1/{当前管理员路径}/migration/xboard`。仅接受 Authorization 请求头；请求及响应禁止缓存；POST 参数只用 JSON（64 KiB 上限）。

- `POST /inspect`：`{host, port, database, username, password, tls}`，只读返回用户统计和两站套餐。
- `POST /preview`：`{source: {...}, plan_mapping: {"源套餐ID": 目标套餐ID}, locking_balance_policy: "discard", confirm_locking_balance: true}`；目标 ID 0 表示明确跳过，返回 `preview_id`、过期时间、计数、阻断项。
- `POST /apply`：`{preview_id, confirm: true}`；无需再次提交源数据库密码。
- `GET /receipt?preview_id=...`：查询当前管理员创建任务的完成记录；编号为 64 位小写十六进制。

成功响应 `{data: ...}`；失败响应 `{message, code}`。`target_write` 明确表示事务未提交；`busy`、`timeout`、`commit_unknown`、网络异常以及 `receipt_not_found` 不可当作安全重试依据。

## 本地验证

```sh
cd go-api
go test ./...
go test -race ./internal/usermigration ./internal/http -run 'Migration|Preview|Source|Apply|Receipt'
cd ../admin-src
npm run check
npm run build
```

另有独立 MySQL → PostgreSQL 集成测试，需显式设置 `MIGRATION_TEST_POSTGRES_DSN` 和 `MIGRATION_TEST_MYSQL_PORT`，默认跳过；仅应连接隔离测试数据库，不能指向生产。测试仅接受本机地址，在随机 schema／database 中运行并清理，MySQL 使用隔离实例的无密码 root 账号创建测试数据与只读测试账号。

本次实际验证通过：

- 全量 `go test ./...`，迁移、HTTP、用户模块的 race 检测，以及 `go vet`。
- 真实 MySQL → PostgreSQL 的 506 个源用户／503 个导入用户流程；包含跨 500 条批次边界、回执幂等、不同管理员隔离。
- 第二批第 501 次写入强制失败后，用户、流量标记和回执全部回滚；目标套餐变更时拒绝旧预览。
- PHP `$2y$` bcrypt 经正式登录和 fresh session 验证通过。
- 导入后正式流量重置任务扫描 502 人、重置 0 人，所有 `u/d` 原样保留。
- 仅获两表 SELECT 权限的真实 MySQL 账号可完成读取和迁移，UPDATE 被拒绝，源用户／套餐快照不变。
- 管理界面 TypeScript 检查、生产构建和 Chromium mock 操作回归；员工直开 URL 也无页面和迁移请求。

此文描述代码能力，不代表已经部署、已填写实际套餐映射或已执行真实用户迁移。
