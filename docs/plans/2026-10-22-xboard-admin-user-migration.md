# 管理后台 Xboard 用户迁移

## 范围与入口

管理员后台 **设置 → 用户迁移**（`/config/user-migration`）。仅完整管理员可用；员工、普通用户不可读取源库或执行迁移。使用当前 V2B Go / PostgreSQL 后端，将 Xboard MySQL 普通用户追加到当前站，不调用旧 `merge-mysql` CLI。

本次已确认的资金策略：**正常迁入用户，但不迁移 `locking_balance` 待解锁佣金**。页面默认 `discard`，仍必须显式勾选确认。它不增加账户余额，也不影响原有普通佣金。

## 操作流程

1. 备份源站和目标站数据库，确认恢复方法；安排源站停止相关写入／切换窗口。
2. 填 MySQL 主机、MySQL 端口（默认 3306）、数据库名、数据库账号和密码。这不是 SSH 登录框，不能把 SSH 端口 2222 当数据库端口。
3. 点击“读取用户与套餐”。数据库连接由 **V2B 后端服务器**发起，不是管理员浏览器发起。
4. 手动选择每个源套餐对应的目标站已有套餐；可以明确选择“不迁入这个源套餐下的用户”。源套餐已删除但仍被用户引用时，也会列出供映射。
5. 核对“强制重生成订阅 Token”和“强制重生成 UUID”两个独立开关（页面默认都开启），确认待解锁佣金处理方式并生成只读预览，核对新增数、实际重新生成数、重复邮箱、权限排除及阻断项。切换任一开关后需重新预览。
6. 完成备份和源数据变化确认，输入 `IMPORT_USERS` 后提交。预览有效期 10 分钟；源站后续变化不自动进入已生成快照，必要时重新预览。
7. 保存迁移编号，等待回执。请求中断、超时或暂时查不到回执**均不能证明导入失败**；先查询同一编号，不要盲目新建迁移。
8. 抽查账号登录、余额、套餐分组、已用流量和重置时间，再安排用户切换到目标站订阅地址。
9. 需要通知本批用户时，在完成回执下的“给本批迁入用户发送邮件”中编辑主题和正文，核对人数、后台发送间隔并明确确认。迁移完成本身**不触发发信**。

推荐只读 MySQL 用户，仅授予源库 `v2_user`、`v2_plan` 的 SELECT 权限；两表必须为 InnoDB。使用内网、受限 SSH 隧道或证书验证 TLS，数据库防火墙仅放行必要来源。TLS 开关开启后验证服务器证书，不跳过验证。不要开放 MySQL 给所有公网地址。

## 数据处理规则

| 数据 | 处理 |
|---|---|
| 源管理员／员工 | 排除，不降级迁入，不复制后台权限 |
| 目标已有邮箱 | 去首尾空白、不区分大小写比较；整条跳过，原密码和权益不变 |
| 源内重复邮箱 | 第一条普通用户记录优先，其余跳过；预览显示计数 |
| 用户密码 | 保留兼容 bcrypt 哈希，不导出明文；不支持的格式阻止导入 |
| 余额、普通佣金、封禁状态 | 保留，不因迁移解封 |
| 流量额度、已用上／下行、到期时间 | 保留源值，NULL 与 0 不混同；不按目标套餐重新赠送额度 |
| 套餐／权限组／设备数／限速 | 套餐必须映射；使用选定目标套餐的设置，不复用源 group ID |
| 无套餐用户 | 保留原额度、用量、到期和资金；目标 plan/group 为空，不自动赋予目标套餐权限 |
| 流量重置 | 使用目标套餐／系统周期；导入同一事务写入当前周期标记，避免第一次日扫清掉已用流量；不复制 Xboard `next_reset_at` |
| Token／UUID | 页面默认强制重生成所有本次新增用户的 Token 和 UUID，两项可独立关闭；关闭对应开关时保留有效且无冲突的源值，但缺失、无效或冲突时仍自动重新生成；旧域名不会自动接管 |
| 订单、支付流水、节点、邀请码、邀请关系、Telegram 绑定、个性折扣／佣金比例、会话、自动续费 | 不迁移；目标分配新的用户 ID，自动续费关闭 |
| 待解锁佣金 | 默认明确舍弃该字段，用户照迁；源库保持不变 |

这不是持续同步，也不是对同邮箱权益做合并。提交前目标出现相关邮箱、Token／UUID 冲突，或目标套餐发生变化，会要求重新预览。

### 旧库泄露与订阅凭据重生成

- 开关只影响**本次新增的用户**；目标已有邮箱仍跳过，已迁入账号不会因再次迁移而被重置。
- 新凭据使用加密安全随机数，避免与目标现有凭据、本批新凭据及**任何源用户的旧凭据**重复，包括被跳过的源用户。
- 预览只返回数量和开关状态，不返回新 Token／UUID；实际新值在预览时产生并绑定任务，确认导入时沿用同一快照，幂等重试不会再次更换。
- 开启任一项后，用户需要重新获取目标站订阅并更新客户端。Token 与 UUID 防护不同，若担心旧库泄露，建议保持两项都开。
- 源库仍为只读，**旧 Xboard 的凭据不会被撤销，登录密码也没有重置**。本功能不能替代旧站下线／撤销凭据、数据库密码轮换或用户密码处置。

## 一致性与凭据保护

- 源库固定两表、只读 REPEATABLE READ 事务，无用户提供 SQL／DSN／表前缀。
- 用户和流量周期标记、实际新增用户的批次成员 ID、完成回执在目标库同一事务内提交。写入采用 500 用户一批；失败回滚，不部分导入。
- 提交期间短时锁定目标用户／套餐表以防注册和改套餐竞争；应在低峰维护窗口运行。锁等待上限 5 秒，整操作上限约 110 秒。
- 同一迁移编号重复提交返回已完成回执；回执绑定发起管理员。数据库提交结果不确定时禁止自动重试。
- 源数据库密码只在本次请求／当前页面内存，不存配置、localStorage、URL 或业务日志。预览中的用户快照只存在后端内存，过期释放；重启后未提交预览失效。
- `v2_user_migration_receipt` 保存迁移编号、操作者 ID、摘要、计数和时间；`v2_user_migration_member` 只保存迁移编号与本次实际新增用户 ID，不重复保存邮箱、账号密码、Token 或源数据库凭据。
- 不提供“一键删除本次导入用户”；实际完成后需要回滚时应先停写、核对后按数据库备份恢复方案处理，不按时间范围盲删。
- 单次源用户上限 200,000，目标校验上限 2,000,000，内存预览数量和用户总数有上限。大库需要另行安排，不通过无限延长 HTTP 请求处理。
- 多实例部署应保证预览与提交到同一后端实例（或迁移期间单实例）；完成回执存在共享目标库，可跨重启查询。
- 反向代理也应允许此迁移路由的较长响应时间，否则即使后端继续执行，前端也可能先收到网关超时。不要因此自动重提。

## 接口

前缀：`/api/v1/{当前管理员路径}/migration/xboard`。仅接受 Authorization 请求头；请求及响应禁止缓存；POST 参数只用 JSON（一般 64 KiB 上限，邮件正文接口为 1 MiB，解码后仍校验内容长度）。

- `POST /inspect`：`{host, port, database, username, password, tls}`，只读返回用户统计和两站套餐。
- `POST /preview`：`{source: {...}, plan_mapping: {"源套餐ID": 目标套餐ID}, locking_balance_policy: "discard", confirm_locking_balance: true, regenerate_tokens: true, regenerate_uuids: true}`；目标 ID 0 表示明确跳过，返回 `preview_id`、过期时间、计数、阻断项及本次两项开关状态。页面默认发送两项 `true`；旧客户端省略字段时按 `false` 兼容原行为。
- `POST /apply`：`{preview_id, confirm: true}`；无需再次提交源数据库密码。
- `GET /receipt?preview_id=...`：查询当前管理员创建任务的完成记录；编号为 64 位小写十六进制。
- `GET /mail/status?preview_id=...`：返回本批迁入人数、当前可发人数、名单跟踪是否可用、邮件配置／队列可用状态、后台发送间隔和最近邮件任务，不返回邮箱名单或 SMTP 凭据。
- `POST /mail/send`：`{preview_id, request_id, subject, content, confirm: true}`；`request_id` 为新的 64 位小写十六进制随机编号。主题去首尾空白后最多 200 个 Unicode 字符，禁止 CR/LF/NUL；正文去首尾空白后最多 100000 UTF-8 字节。返回邮件任务，不代表邮件已全部发送。

开关随预览快照与完成回执保存；`apply` 不接受覆盖开关的参数。旧回执缺少开关字段时按关闭展示，实际重新生成数量仍以回执计数为准。

成功响应 `{data: ...}`；失败响应 `{message, code}`。`apply` 的 `target_write` 表示导入事务未提交；邮件接口的同名错误不能证明任务未创建。`busy`、`timeout`、`commit_unknown`、网络异常以及 `receipt_not_found` 不可当作创建新任务的依据。

## 迁入用户群发邮件

### 收件范围与频率

- 仅完整管理员可操作，并且只能访问自己创建的已完成迁移批次。
- 收件人从该批次实际新增用户 ID 关联目标库当前用户取得，排除已删除用户及当前管理员／员工，邮箱去重。原有用户、重复邮箱跳过项、源管理员等不会加入批次名单；无套餐但成功迁入的用户会加入。
- 不接受前端传入收件人、用户筛选条件或用户 ID。迁移群发不再访问源 MySQL，不需要重新填写源密码。
- 旧版本回执没有实际成员 ID，`mail_tracking_available` 默认为 false，禁止精准群发；不能按邮箱、日期或连续 ID 猜测名单。本功能上线后新迁移的批次才支持。
- 直接复用后台 `email_bulk_interval`、SMTP 配置、`notify` 模板和现有邮件发送记录。例如设置 5 秒，即本批每两封之间等待 5 秒，最后一封不额外等待；0 表示不额外限速。任务使用提交时配置快照，不新增迁移专属速率设置。这不是多个并行群发任务之间的全局限流。

### 重试、状态与队列限制

- 每次有意发送生成一个新 `request_id`。数据库保存请求编号、内容 hash、操作者、计数、状态和时间，不保存邮件正文或额外邮箱列表。任务按单调序号排序，支持同一秒多次操作。
- 相同请求编号及相同内容返回原任务，不重新入队；相同编号但不同内容拒绝。receipt 行锁和唯一索引阻止多实例／并发请求重复创建；同批次已有排队或发送中的任务时禁止开启新任务。
- 浏览器仅在当前标签页的 `sessionStorage` 暂存**待确认的邮件请求**以保留原编号／正文，页面内换页和刷新后可恢复并使用原请求重试；收到确认结果或明确拒绝后清除。不保存源数据库凭据，不自动重试发信。关闭标签页后若请求结果仍未知，应先恢复回执、查询任务并核查记录，不能盲目重建。
- 使用已有 `send_email_mass` 队列，生产 Runtime 通过非阻塞 `TryEnqueue` 入队；队列满则记录 `queue_failed`，不回退到 HTTP 同步发送。提交记录与入队之间不是原子事务；提交结果未知或进程崩溃时不得自动重新发送。
- 状态：`queued`（排队）、`running`（发送）、`completed`（全部 SMTP 接受）、`partial_failed`（已尝试完但部分失败）、`interrupted`（未全部尝试）、`queue_failed`（未成功入队）。`sent` 仅表示 SMTP 接受，不保证终端邮箱最终收到。
- 每次 SMTP 尝试后更新成功／失败计数，单封失败后继续下一封；计数持久化失败会停止后续发送，避免未记录的批量发送。取消后使用独立短超时保存已尝试计数。既有 SMTP 调用不接收 context，正在执行的单封调用无法强制中止，只能在下一封或间隔等待时停止。
- **现有队列为进程内队列，不支持重启自动续发。**硬重启可能留下旧 `queued/running` 状态；不要自动清除活动任务或补发。先核查服务和邮件发送记录，再进行受控处理。按 5 秒发 19000 人，仅间隔就约 26.4 小时，期间应避免重启相关服务。
- 原任务结束后可以明确点击“编辑新邮件”再次群发，但这是**整个批次重发**，不是只重试失败收件人，已发送用户也会收到新邮件。

本功能没有给现有用户管理群发增加独立频率，也没有自动发送迁移完成通知；管理员必须填写并确认内容。

## 本地验证

```sh
cd go-api
go test ./...
go test -race ./internal/usermigration ./internal/http -run 'Migration|Preview|Source|Apply|Receipt'
cd ../admin-src
npm run check
npm run build
```

另有独立 MySQL → PostgreSQL 集成测试，需显式设置 `MIGRATION_TEST_POSTGRES_DSN` 和 `MIGRATION_TEST_MYSQL_PORT`，默认跳过；仅应连接隔离测试数据库，不能指向生产。测试仅接受本机地址，在随机 schema／database 中运行并清理，MySQL 使用隔离实例的无密码 root 账号创建测试数据与只读测试账号。

本次实际验证通过：

- 全量 `go test ./...`，迁移、HTTP、用户模块的 race 检测，以及 `go vet`。
- 真实 MySQL → PostgreSQL 的 506 个源用户／503 个导入用户流程；包含跨 500 条批次边界、回执幂等、不同管理员隔离。
- 第二批第 501 次写入强制失败后，用户、流量标记和回执全部回滚；目标套餐变更时拒绝旧预览。
- PHP `$2y$` bcrypt 经正式登录和 fresh session 验证通过。
- 导入后正式流量重置任务扫描 502 人、重置 0 人，所有 `u/d` 原样保留。
- 仅获两表 SELECT 权限的真实 MySQL 账号可完成读取和迁移，UPDATE 被拒绝，源用户／套餐快照不变。
- 管理界面 TypeScript 检查、生产构建和 Chromium mock 操作回归；员工直开 URL 也无页面和迁移请求。
- 本轮邮件验证：真实隔离数据库上的批次成员归属、无套餐成员、回滚、两批隔离、旧回执禁止群发、8 个并发相同请求只入队一次、同秒最新任务、失败／中断任务不自动重发。
- 邮件适配器使用 fake SMTP／fake sleep 验证后台 5 秒间隔及 0 不额外等待；任务准备不发信，取消／计数写入失败停止后续发送。队列满非阻塞拒绝、并发关闭和 race 检测通过。
- Chromium mock 验证邮件明确确认、重复点击保护、网络失败后刷新页面恢复原编号和原内容、浏览器存储不可用时不发送、状态读取失败禁发，以及 390px 移动端布局。以上测试不向真实用户发送邮件。

此文描述代码能力，不代表已经部署、已填写实际套餐映射或已执行真实用户迁移。
