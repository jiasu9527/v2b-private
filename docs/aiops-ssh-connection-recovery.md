# AI 运维 SSH 连接失败恢复

## 区分动作失败与整轮任务失败

SSH 在发送 exec 之前进行最多三次连接尝试（每阶段最多十秒，重连间隔一／二秒，仍受动作总时限约束）。重试耗尽不证明远程命令曾执行，也不应终止针对其他主机的独立任务。

- SSH worker 将连接阶段、错误类别、是否临时错误、实际尝试次数与 `execution_state=not_executed` 保存在 `v2_ai_action.ssh_setup_failure`。
- 仅本地连接／会话建立函数生成标记，不从远程输出、中文错误字符串或模型参数推断。状态必须为 `ssh_command/failed`，没有退出码，服务器 ID、阶段、类别和尝试次数均有效。
- 自动执行返回 `recovery=ssh_setup`，而不是将其升级为整轮硬停止。动作仍是失败，不能将失败操作写成成功。
- 同一模型批次中的剩余调用可能依赖此前成功，全部跳过。下一次模型请求读取真实结果、重新规划其他独立任务。
- 故障服务器本轮 SSH 预算用完，`propose_ssh_command` 换命令和 `ssh_status` 都不能重新拨号；其他服务器可继续。恢复信息在动作上下文与本轮系统上下文中保留，避免历史压缩丢失。
- 认证／主机指纹／协议错误不盲重试，跳过主机并提示修正配置；临时网络错误才使用上述连接重试。

## 必须继续停止的情况

用户停止、授权撤回、动作总时限取消，或命令发送后断线导致 `unknown`，均不能用建立连接失败恢复路径放行。已知非零退出仍采用原有“核对现状后修正命令”的路径。旧记录没有结构化证据时不根据错误中文补写可信标记；操作人新发消息后重新查询规划，旧动作保持原始结果。

## 回归

- `ssh_setup_failure*_test.go`：JSON 严格验证、无 exec 前生成、执行后不生成、数据库原子持久化、旧记录与损坏标记不放行。
- `ssh_setup_recovery*_test.go`：真实 SSH/TCP fixture（不启动 shell）与 PostgreSQL；三次连接失败后仍请求模型、跳过同批依赖命令、其他主机执行一次、换命令／工具不能绕过预算、新用户轮次可重新尝试。
- 原连接重试、撤权、用户停止、执行后未知不重放及非零退出恢复测试继续运行。

部署为附加 JSONB 列，不修改旧动作、不自动续跑历史失败命令。新版后台服务启用后，下一次用户任务使用新逻辑。
