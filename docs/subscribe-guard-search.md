# 订阅防护组合筛选

后台「订阅防护」将原来的账号搜索与 UA 搜索合并。可同时选择邮箱／用户 ID、入口分配规则及固定子组、UA、拉取时间和放行／拦截结果；不同条件之间为 **AND**。结果按用户去重，可按最近拉取时间或匹配次数排序、分页。

例如：选择「VIP 入口」规则、UA 包含 `Forest`、最近 24 小时、已放行，即查询在这段时间有放行请求，且该请求 UA 包含 `Forest`，用该请求 UA 与用户当前资料重算后命中该入口规则的用户。

## 统计口径

- UA、时间、请求结果及入口规则必须由**同一条请求**满足，不能拿一条请求的 UA 配另一条请求的时间。
- 入口归属使用**当前规则、当前用户资料、已保存的固定子组归属**计算，不代表请求当时的历史归属。不同节点范围按各自规则优先级判定，所以一位用户可能显示多条入口规则。查询不新建或重分配固定子组。
- 当前规则匹配不等于已成功下发入口或下载成功；节点可见性、账户资格、订阅生成与客户端后续处理仍由原订阅流程决定。「已放行」仅表示通过订阅防护。
- 匹配次数、独立 IP／UA 数、最近拉取时间及匹配记录，只计算本次筛选命中的请求，而不是该账号的全部历史。
- 仅按账号／入口规则查询时，可包含无匹配拉取记录的账号（0 次）；附加 UA、拉取时间或放行／拦截条件后，必须有满足条件的请求。
- 没有拉取记录时，未知 UA 不能当成实际空 UA。无法确定 UA 规则及其优先级时明确标注「入口规则无法确定」，不虚构命中；按具体规则查询只纳入能够确定命中的用户。
- 先完成筛选并计算去重用户总数，再分页；切换页码沿用已经提交的筛选条件。
- 不增加日志，也不修改订阅分配行为。数据限于现有订阅防护日志；未开启记录、已清空或超出保留期的请求无法还原。日志保留天数为 0 表示不自动清理。

## 管理 API

`GET /api/v1/<admin_path>/subscribe-guard/search`

仅管理员可用，响应禁止缓存。旧 `user-search`、`ua-search` 接口保留兼容；用户网站及 App 不需要修改。

| 参数 | 说明 |
| --- | --- |
| `account` | 邮箱或用户 ID；纯数字按用户 ID 精确匹配 |
| `account_match` | 邮箱 `contains`（默认）或 `exact` |
| `policy_id` | 当前入口规则 ID |
| `group_id` | 该规则下的固定子组 ID；必须同时指定所属规则 |
| `ua` | UA 筛选内容 |
| `ua_match` | `contains`（默认）、`equals`、`not_contains` |
| `start_at` | 开始 Unix 秒，包含该时刻 |
| `end_at` | 结束 Unix 秒，不包含该时刻；与开始时间组成半开区间 |
| `result` | `all`（默认）、`allowed`、`blocked` |
| `sort` | `last_at`（默认）或 `count`，降序 |
| `current` / `page_size` | 默认 1 / 20，单页最多 100 |

返回顶层 `data`（用户数组）、`total`、`current`、`page_size`、`matched_events`、`unresolved_events`、`log_keep_days`、`available_from`、`available_to`、`rule_basis: "current"`、`warnings`。

每个用户包含基本账号／套餐状态、`count`、`allowed`、`blocked`、`ip_count`、`ua_count`、`first_at`、`last_at`、`recent` 及 `entry_policies`。`recent` 最多 20 条，只包含匹配请求的时间、IP、UA、状态和原因；不返回订阅 Token。`entry_policies` 提供父规则 ID／名称、固定子组 ID／名称（普通规则为 0／空）、动作、入口地址及计算使用的 UA。`entry_policy_uncertain` 表示无日志 UA 导致部分入口规则无法确定；兼容字段 `entry_policy` 仅取首项，新页面应使用数组。

时间范围以 Unix 秒传输，管理界面按浏览器本地时区选择并显示。`available_from/to` 用于提示实际可查询的保留日志范围，并不保证每个时刻均有记录；`unresolved_events` 表示符合事件条件但无法关联到当前账号的请求，不保证这些请求命中了所选入口规则。带账号条件时无法确定未知请求属于该账号，因此该字段为 0，避免把其他账号的旧 Token 误报为当前账号异常。读取日志或加载规则失败时应返回明确错误，不静默用最近 1,000 条内存记录充当全量结果。

界面要求至少一个有效条件，时间选择要求开始和结束完整。API 允许单边时间及空条件；空条件只返回有保留请求的用户，不自动列出无请求用户。UA 匹配忽略大小写并去除首尾空白，邮箱包含按字面子串匹配（`%`、`_` 不作为 SQL 通配符）。

## 大范围查询与限制

查询直接只读扫描现有文件，不新增索引表或访问日志。后端最多运行 20 秒，原始日志文件最多 512 MiB、符合事件条件的候选记录最多 50 万条、候选用户最多 5 万位、不同用户／UA 规则评估最多 10 万组、需额外解析的旧 Token 最多 1,000 个。超过限制会明确报错，不截断后伪装为完整总数。

日志扫描和旧 Token 解析在账号过滤前进行，所以仅填写精确邮箱不一定能绕过候选事件／旧 Token 限制；应同时缩小拉取时间或 UA。原始文件超过上限时，仅缩小查询范围无效，需按现有后台设置调整日志保留期并等待清理，或由运维归档日志。查询不会自行删除日志。

读取长度以打开文件时为界，查询期间新追加的记录留给下次查询。检测到读取错误、坏 JSON 或文件截短时不返回部分结果；这不是跨数据库与日志文件的事务快照，实时请求、用户状态和规则变更可能使连续两次查询略有差异。

## 发布检查

更新 Go 后端和管理端构建产物，不需要数据库迁移。管理端仍保持单个自包含 `admin.js`，遵守带 `?v=` 版本参数的资源加载约定，避免产生两份 React。

回归至少覆盖：同条请求组合筛选、不同节点规则优先级、固定子组归属、过滤后分页、无记录用户、时间边界与保留期、旧请求取消、筛选后翻页、重置及生产构建页面加载。

```sh
cd go-api
go test ./...
go test -race ./internal/admin ./internal/http
go vet ./...
cd ../admin-src
npm run check
node --test scripts/test-*.mjs
npm run build
```
