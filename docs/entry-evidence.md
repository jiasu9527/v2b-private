# 入口异常排查与历史下发证据

## 后台入口与操作顺序

在 **节点管理 → 入口分配 → 异常排查** 使用本功能，不新增侧栏菜单。

1. 从入口检测跳转，或手动填写入口规则／固定子组、实际下发 IP／域名、端口与时间范围。默认端口为 `54101`；时间按**记录完成时间**筛选，开始含、结束不含，页面使用浏览器本地时区。可叠加 UA 包含及精确用户 ID／邮箱。
2. 在「历史下发」展开请求，核对真实生成节点、规则／子组、实际写入入口、响应状态与证据覆盖；在「异常候选」查看去重用户及每人的证据引用。
3. 明确选择「冻结选中」或「冻结全部匹配」。冻结只保存排查证据及名单，**不会封禁用户，也不改变入口**。单人候选可以留档，但不能执行二分。
4. 在轮次档案预览 A／B／R 去向，选择健康备用 IP 池或填写两个不同入口，确认后才写入二分。后台再次校验版本、名单、当前路由及备用 IP 占用；冲突应重新查询／预览，不应重复提交旧快照。
5. 执行后观察 A／B 下发覆盖及探针结果，人工记录「正常／单组复现／两组异常／未复现／证据不足」。可继续排查 A／B，形成带父轮次的档案。轮次关系树只展示**当前页已加载**的档案；跨页父档案可点击查看，不代表整棵历史树已完整加载。

## 什么算证据

- 采集发生在真实节点生成、响应写入路径，包含请求／用户、UA、节点与规则快照、实际下发地址及端口。服务端写入完成不证明客户端已收到、导入或建立连接。
- 只有 2xx、响应完成且 `coverage=complete` 的相关记录才进入已证实下发候选；仍需校验当前规则是否覆盖该用户。304、写入失败、部分覆盖不得当作完整新正文下发。
- 候选证据引用有展示上限；`evidence_total`／`evidence_truncated` 会说明省略情况。规则 `revision` 是当前配置版本，节点 `rule_revision` 是当时下发快照，不应混用。
- 当前采集能追溯规则／固定子组及 Forest provider；历史入口合集归属尚未采集，`collection_id=0` 表示没有该项快照，不应解释成确定未属于合集。
- 「历史暴露与证据缺口」是独立背景表，不自动加入冻结名单。历史暴露表示窗口前已有完整相关记录，可能仍有缓存；“仅请求”只纳入存在目标节点关联但响应／覆盖不完整的记录。完全无法关联目标的请求只提示缺口，不能把全站无关用户混入入口名单。
- 用户已删除时仍可展示历史 ID／邮箱；“无记录”不等于“没有获得过入口”。TCP 失败和用户相关性均不能单独证明封锁或恶意行为。
- **旧订阅放行日志无法追补真实历史下发**：缺少当时入口及节点快照的记录不会通过当前规则反算成历史事实。功能上线前、日志写入失败或超出保留期的情况应明确视作证据缺口。

## 冻结二分的安全边界

- 当前支持已启用的覆盖入口规则／固定叶子，要求有生效节点、入口非空、不属于入口合集、没有额外下发节点，且优先级可安全扩展。标准规则只接受**一个用户 ID 范围＋可选 UA 条件**；其他复杂条件先只查询，不绕过服务端限制强行二分。
- 冻结绑定候选 hash、规则快照及当前拓扑。候选必须与当前有效路由和请求 UA 对应；不能把其他入口或不匹配 UA 的用户带入。
- 至少两个选中用户才可二分。保留原节点、端口和 UA 条件，不将有 UA 约束的入口变为全 UA 覆盖。
- 普通规则创建固定名单覆盖层，原动态规则继续处理其他用户；固定叶子将选中用户分到 A／B，未选中者保留原入口，必要时创建 R 子叶。其他叶子不变。
- 备用 IP 池在**执行时**原子领取；预览不预留。要求端口匹配、启用、未隔离、未被规则占用，且符合现有探针健康条件。不以其他端口检测通过代替目标端口健康。
- 手动入口不会假装已检测健康，操作前应核对目标端口的探针结果；两地址不得相同、等于原规则入口或本次调查的已暴露地址。
- 存在生效中的人工用户入口覆盖时，拒绝冻结二分，防止新覆盖层绕过原有后置路由；应先核对该覆盖再重新预览。当前命中校验不是账户可用性／节点权限的完整模拟。
- 执行档案不可再次创建同轮分组。入口规则写入不意味着客户端立即切换，也不回滚已经缓存的旧入口。

## 检测继承与观察

普通规则创建覆盖层时会尝试继承来源入口检测配置及绑定探针。档案执行结果展示 `monitoring_status` 和 `monitoring_warning`：

- `inherited`：已继承检测配置，不代表探针已返回健康结果。
- `unconfigured`：来源没有启用检测，新规则不会擅自开启；需要手动配置检测。
- `deferred`：检测配置争用／校验失败，路由二分可能已经完成，检测未完成继承；按提示手动启用，不要重新执行二分来“重试检测”。

观察表显示固定人数、已记录服务端下发人数、尚无记录人数及观察时长。后台每 5 分钟刷新已执行轮次，原始日志每小时尝试清理，先刷新累计覆盖再清理；刷新失败会延后清理。累计覆盖按用户去重保存在独立表中，原始日志清理不删除已累计的人数；采集或后台刷新中断超过保留期可能遗漏证据，页面会提示保留期缺口。人数不能解释成实际在线人数，也不能把尚无记录人数称为“未拉取人数”。

「观察与结论」还提供低调折叠的**本轮探针事件**：仅归档本轮执行后 A／B 对应检测入口的真实 `down`／`recovered` 事件，保留探针、目标、时间、地址和检测时解析 IP（如原事件有记录）。事件随档案独立保存，普通检测日志超过 24 小时被清理后，已归档事件仍可查看。页面按发生时间倒序展示最近 100 条，并显示归档总数及展示截断提示；这不是只保留 100 条。

后台归档间隔超过普通检测日志保留期时，`probe_events_gap` 会提示不可追补的缺口。没有事件不能推断入口正常，掉线／恢复也不自动认定为“被墙”或归责用户。冻结前的来源检测快照与执行后的 A／B 事件是不同证据，不相互替代。

## 保留期与权限

- 原始下发请求／节点默认保留 **30 天**，管理员可在「记录保留」设置 **1～365 天**；清理由后台按保留期执行，缩短设置不是即时清空所有记录。
- 冻结名单、冻结证据、人工观察、累计覆盖及本轮探针事件独立于原始日志保存，不随原始日志过期自动删除。
- 管理员在上述页面操作；员工可经现有 AI 运维业务操作目录查询、冻结、预览／执行及记录观察，本次不另开放整个节点管理页面。**只有管理员可删除档案和调整记录保留期**。
- 删除档案会删除其冻结名单、累计覆盖和已归档探针事件，**不会回滚已执行的入口规则**。历史父档案删除后，子档案中保留的父编号不再保证可打开。
- 观察结论编辑中刷新覆盖／翻名单页会保留草稿；保存使用原草稿版本防止覆盖他人更新。

## 部署与当前未覆盖范围

部署必须同时更新 **Go 后端与管理端静态资源**，不能只替换前端脚本。新表在运行时初始化，安装／升级 SQL 同步维护于 `database/install.pgsql.sql` 和 `database/update.pgsql.sql`；升级不得执行含 DROP 的全新安装 SQL。既有数据库按原项目升级流程处理并先备份。

这期交付是“真实下发 → 候选冻结 → 安全二分 → 轮次观察”基础链路。**第二批对照组、自动跨轮归因／交叉分析、自动置顶及完整全量轮次树尚未实现**；不会把相关性自动判为恶意，不以无证据的自动归因代替人工结论。
